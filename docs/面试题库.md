# 面试题库

这份文档用于准备 `interview-assistant` 项目面试。每道题都按下面四个角度回答：

1. 替代方案：为什么没有选择另一条路。
2. 代价：当前方案牺牲了什么。
3. 失败场景：什么时候会失败，如何发现。
4. 当场改动：现在修改哪里，如何验证。

回答时不要只背结论。先讲当前项目的真实实现，再主动补充“当前是学习阶段的过渡方案，后续如何向远程 `interview-guide` 演进”。

## 快速记忆模板

每道题都用这句话提醒自己：

```text
我为什么选它？
它牺牲了什么？
它什么时候会坏？
现在让我改，我改哪里、怎么验？
```

项目回答最好按这个顺序展开：

```text
背景 -> 方案 -> 替代方案 -> 代价 -> 失败处理 -> 验证和后续演进
```

## 1. 为什么用 Tika，而不是自己写 PDF 解析？

### 30 秒回答

项目需要支持 PDF、DOC、DOCX、TXT 等多种简历格式。Apache Tika 已经封装了文件类型识别和常见文档文本抽取能力，所以我把解析能力放在 `infrastructure/file` 层，通过统一的 `DocumentParseService` 输出简历文本。这样业务层只关心“得到干净文本后如何分析”，不需要为每种文件格式维护一套解析器。

### 1. 替代方案：为什么不用别的方案

- 自己解析 PDF：需要处理字体、分页、编码、图片、扫描件等细节，维护成本高。
- 只使用 PDFBox：PDFBox 对 PDF 很强，但还要另外处理 DOCX、DOC、TXT，格式适配会分散到多个库。
- 让 AI 直接读取文件：模型接口、文件大小和隐私传输都会增加不确定性，且无法替代基础文本抽取。

Tika 更适合当前阶段，因为它提供统一入口；如果后续出现扫描 PDF，再单独增加 OCR 能力，而不是推翻 Tika。

### 2. 代价：牺牲了什么

- Tika 对复杂排版和扫描图片不是完美解析器。
- 表格、双栏排版、图片文字可能丢失顺序或内容。
- 解析大文件会占用 CPU 和内存。

所以项目仍需要文件类型校验、大小限制、文本清洗和解析异常处理，不能把 Tika 当成“任何文件都能正确解析”。

### 3. 失败场景：什么时候会崩、怎么发现

- 上传损坏文件：解析抛异常，接口返回简历解析失败。
- 上传扫描版 PDF：解析结果为空或内容很少。
- 超大文件：解析耗时过长或内存压力升高。
- 不支持的格式：在文件校验阶段拒绝，而不是进入 AI 分析。

发现方式：查看上传接口响应、后端解析日志、保存的简历文本长度，并对空文本做业务校验。

### 4. 当场改：现在让我改什么

我会在 `DocumentParseService` 增加文本为空检测和解析耗时日志；如果要支持扫描 PDF，再新增 OCR 适配器，不把 OCR 代码混进 Controller。

验证方式：准备正常 PDF、损坏 PDF、扫描 PDF、超大文件各一份，分别检查响应状态、错误码、日志和数据库中的解析结果。

### 记忆方法

```text
Tika = 多格式统一入口
代价 = 复杂排版和扫描件不完美
验证 = 文件类型、文本长度、解析耗时
演进 = OCR 作为独立适配器
```

代码定位：`server/src/main/java/com/interview/infrastructure/file/DocumentParseService.java`

## 2. 为什么简历原文件放 RustFS/S3，不直接存 PostgreSQL？

### 30 秒回答

数据库保存简历的元数据、哈希、解析文本和分析结果；原始 PDF/DOCX 文件放到 RustFS 这类 S3 兼容对象存储。数据库适合结构化查询，对象存储适合大文件保存和后续扩展。业务表只保存对象 Key，不把二进制内容塞进关系表。

### 1. 替代方案

- 存 PostgreSQL `bytea`：实现简单，但会增大数据库备份、复制和查询压力。
- 存本地磁盘：单机开发简单，但多实例部署、备份和迁移麻烦。
- 使用云厂商对象存储：生产可行，但本地学习成本和费用更高。

RustFS 兼容 S3 API，所以当前可以本地开发，后续切换 MinIO 或云对象存储时业务代码变化较小。

### 2. 代价

- 数据库记录和对象文件存在两个系统，不能天然保证同一事务。
- bucket 权限、Access Key、Secret Key 配置错误会导致上传 403。
- 删除简历时必须考虑数据库记录和对象文件的清理顺序。

### 3. 失败场景

- 对象存储不可用：简历上传失败或启动时 bucket 检查报错。
- 数据库记录保存成功、对象上传失败：出现不完整简历记录。
- 数据库记录删除、对象文件未删：产生孤立对象。

发现方式：记录 `resumeId`、对象 Key 和错误堆栈；对上传和删除分别设计补偿或重试策略。

### 4. 当场改动

我会先给上传流程增加明确的状态字段，例如 `UPLOADING`、`UPLOADED`、`FAILED`，再把对象上传和数据库落库拆成可恢复步骤。验证时模拟 RustFS 停止、错误凭证和重复上传，检查状态是否可解释。

### 记忆方法

```text
数据库管结构化数据，对象存储管大文件
代价是跨系统一致性
失败重点看 403、孤立文件、半成功记录
演进方向是任务状态和补偿机制
```

代码定位：`server/src/main/java/com/interview/infrastructure/file/FileStorageService.java`

## 3. 为什么 AI 失败后要规则兜底？

### 30 秒回答

AI 是外部依赖，可能出现超时、401、404、返回 JSON 格式错误或题量不足。项目把 AI 出题和 AI 评估都包在 Service 层，失败时使用当前 Skill 的规则题或规则评分，保证面试创建、答题和报告主流程不中断。

### 1. 替代方案

- AI 失败直接返回错误：实现简单，但用户无法继续面试。
- 无限重试：可能放大延迟和费用，还会让接口长时间卡住。
- 只使用规则题：稳定，但缺少结合简历的个性化问题。

当前选择是 AI 优先、规则兜底，兼顾体验和可用性。

### 2. 代价

- 规则题质量不如 AI 个性化题。
- 用户可能不知道当前使用了降级结果。
- 同步调用仍然会产生等待时间，兜底只解决失败，不解决延迟。

### 3. 失败场景

- API Key 无效：返回 401。
- Base URL 拼错：返回 404，例如曾经出现过 `/v1/v1/chat/completions`。
- AI 返回题目数量不足：需要归一化并用规则题补齐。
- 答案评估调用失败：保存答案后改用规则评估。

发现方式：后端日志记录业务 ID 和异常堆栈，但不记录 API Key；接口响应仍要能返回可继续的业务结果。

### 4. 当场改动

我会把重试和降级策略抽成独立组件：短超时、有限重试、结构化输出修复、最终规则兜底。验证时用 Mockito 模拟 AI 抛异常、返回空 JSON、返回不完整题目，确认主流程和最终题量仍正确。

### 记忆方法

```text
AI 优先，规则兜底
代价是质量下降，不是流程中断
失败看 401、404、超时、JSON 和题量
改动重点是重试、修复、降级三层
```

代码定位：`InterviewQuestionService`、`InterviewAnswerEvaluationService`

## 4. 为什么要设计 Skill，而不是把 Java 题目写死？

### 30 秒回答

Skill 把面试方向的 Persona、分类和题量优先级从 Java 代码中抽离到资源文件。当前支持 `java-backend` 和 `system-design`，同一套 Service 通过 `skillId` 加载不同配置，规则兜底和 AI Prompt 使用同一份 Skill 信息。

### 1. 替代方案

- `if/else` 写死每个方向：开始快，但方向一多就难维护。
- 每个方向复制一个 Service：隔离明显，但重复代码多。
- 全部放数据库：灵活，但当前学习阶段会增加配置管理、版本和迁移复杂度。

资源化 Skill 是当前阶段最简单的配置驱动方案。

### 2. 代价

- 配置错误要到启动或创建面试时才暴露。
- 资源文件变更通常需要重新部署。
- 当前 Skill 结构还没有数据库版本和后台编辑能力。

### 3. 失败场景

- Skill ID 不存在：业务校验失败。
- `SKILL.md` 缺少 front matter：启动加载失败。
- `skill.meta.yml` 分类为空：题量分配或兜底题不符合预期。

发现方式：Skill 加载测试、非法 Skill 测试、接口查询 `/api/interview/skills`，以及检查创建面试的题目分类。

### 4. 当场改动

增加第三个 Skill 时，只需要新增资源目录和元数据，再补加载与题量分配测试；如果未来要在线编辑，再把 Skill 配置抽到数据库并增加版本校验。

### 记忆方法

```text
Skill = Persona + 分类 + 配额
优点是配置驱动，代价是配置不热更新
失败重点看资源格式和非法 ID
扩展方向是新增资源，不复制 Service
```

代码定位：`server/src/main/java/com/interview/modules/interview/skill/InterviewSkillService.java`

## 5. 为什么答案要拆到独立表，不能只改 questionsJson？

### 30 秒回答

`questionsJson` 现在只保存本场面试生成时的题目快照，用户答案、评分、反馈、参考答案和关键点放在 `interview_answers`。这样可以支持暂存、提交、单题评估、历史详情和报告聚合，也避免不断修改整段 JSON。

### 1. 替代方案

- 所有答案直接写回 `questionsJson`：MVP 快，但局部更新、并发和查询都不方便。
- 每场面试一张答案 JSON：结构灵活，但单题查询和统计困难。
- 独立答案表：多写一张表，但关系清晰、可查询、可扩展。

### 2. 代价

- 查询详情需要把题目快照和答案表重新聚合。
- 删除会话时需要处理答案级联。
- Entity、Repository、Service、DTO 都比单 JSON 方案多。

### 3. 失败场景

- 答案保存成功、会话索引更新失败：用户看到的进度可能不一致。
- 同一题重复提交：需要 upsert 或唯一约束。
- 题目快照和答案表题号不一致：报告聚合错位。

发现方式：检查 `questionIndex`、答案表唯一约束、报告中的已答题数量和题目对应关系。

### 4. 当场改动

如果要支持答案草稿版本，我会增加 `answerVersion` 或答案历史表，而不是继续扩大 `questionsJson`。验证时测试暂存不推进、提交推进、重复提交和完成后禁止提交。

### 记忆方法

```text
questionsJson 是题目快照
interview_answers 是作答事实
代价是查询时需要聚合
关键验证是 questionIndex 对齐
```

代码定位：`InterviewSessionEntity`、`InterviewAnswerEntity`、`InterviewQuestionAnswerAggregator`

## 6. 为什么当前 AI 调用是同步的？

### 30 秒回答

当前项目先用同步调用跑通业务闭环：创建面试时同步出题，提交答案时同步评估。同步方案更容易学习 Controller、Service、AI、持久化之间的调用关系，也保留规则兜底。它是过渡方案，后续参考项目会演进为 Redis Stream 异步任务和状态查询。

### 1. 替代方案

- Redis Stream 异步：体验和稳定性更好，但要引入任务状态、消费组、重试、幂等和前端轮询。
- 消息队列：能力更强，但当前项目运维成本过高。
- 本地线程池：比同步快，但进程重启会丢任务，不能解决可靠投递。

### 2. 代价

- 创建和提交接口会等待远程 AI，页面出现“创建中”“提交中”。
- 外部服务慢时占用 Web 请求线程。
- 超时、重试和任务恢复能力不足。

### 3. 失败场景

- AI 服务响应慢：浏览器请求长时间 Pending。
- 进程在 AI 调用期间重启：本次任务状态可能不完整。
- 用户重复点击：可能产生重复请求。

发现方式：查看 Network 请求耗时、后端 AI 调用耗时日志、任务状态和重复会话数量。

### 4. 当场改动

第一步不是直接上 Redis，而是先增加 AI 超时和调用耗时日志；第二步为创建面试增加 `requestId` 幂等；第三步再把评估任务写入 Redis Stream，并增加 `PENDING/RUNNING/SUCCESS/FAILED` 状态。

### 记忆方法

```text
同步 = 先跑通、容易解释
代价 = 慢、不可恢复、重复请求风险
演进 = 超时 -> 幂等 -> Redis Stream
```

### 代码定位

当前实现：`InterviewQuestionService`、`InterviewAnswerEvaluationService`。

参考实现：Gitee `interview-guide` 的 Redis Stream Producer/Consumer 和任务状态模型。

## 7. 为什么使用 `questionsJson`，而不是一开始拆题目表？

### 30 秒回答

当前阶段使用 `questionsJson` 保存一场面试生成时的题目快照，因为题目结构还在快速迭代，JSON 能让 MVP 快速跑通。用户答案已经拆到独立答案表，说明我们只把仍然稳定的题目快照留在 JSON 中。等出现题库管理、题目搜索、统计和多轮追问，再拆成独立题目表。

### 1. 替代方案

- 一开始就拆 `interview_questions`：结构更规范，但迁移和关联复杂度提前增加。
- 全部存 JSON：开发快，但查询和局部更新困难。
- 题目独立表 + 会话关联表：长期更好，但不是当前 MVP 的最小方案。

### 2. 代价

- 不能方便地按题目分类、题面全文检索。
- 历史题去重需要解析 JSON。
- JSON 结构变更需要兼容旧快照。

### 3. 失败场景

- AI 返回结构变化导致旧 JSON 无法反序列化。
- JSON 过大导致会话查询和 Prompt 变慢。
- 题目字段缺失导致前端展示异常。

### 4. 当场改动

如果要支持题库管理，我会增加独立题目表和迁移脚本，同时保留旧 `questionsJson` 作为历史快照，先做双读，再逐步停止写旧字段。验证要覆盖旧快照读取、迁移后题目顺序和报告聚合。

### 记忆方法

```text
JSON 是过渡快照，不是最终题库模型
代价是查询和迁移困难
演进是双读迁移，不直接删旧字段
```

## 8. 为什么 Service 抛 `BusinessException`，而不是直接抛 RuntimeException？

### 30 秒回答

业务失败需要稳定的错误码和用户可理解的消息。例如简历不存在、面试已完成、Skill 不存在，都应该通过 `BusinessException + ErrorCode` 统一表达，再由 `GlobalExceptionHandler` 转成 `Result.error`。这样 Controller 不需要重复写异常转换逻辑。

### 1. 替代方案

- 直接抛 `RuntimeException`：代码少，但错误语义不稳定，前端难以判断。
- Controller 每个接口手动 try/catch：重复、容易漏处理。
- 使用 HTTP 异常体系：可以更 REST 化，但当前项目统一响应结构已经确定。

### 2. 代价

- 需要维护错误码表。
- 全局异常处理器必须持续覆盖新的异常类型。
- 当前统一响应保留 HTTP 200、业务码区分，和纯 REST 状态码风格不同。

### 3. 失败场景

- 新增业务异常但忘记加入错误码。
- 异常消息泄露内部路径或第三方密钥。
- 未知异常被错误包装成成功响应。

### 4. 当场改动

新增一个“简历重新分析”接口时，我会先增加领域错误码，再在 Service 抛 `BusinessException`，最后补全局异常和 Controller 测试。验证正常、资源不存在、参数非法三种响应。

### 记忆方法

```text
Service 讲业务错误
Handler 统一转换
Controller 不写 try/catch 流程
```

## 9. 为什么前端使用 Vite Proxy？

### 30 秒回答

前端开发服务器运行在 `5173`，后端运行在 `8080`，浏览器会认为这是跨域请求。项目让 Axios 只请求相对路径 `/api`，再由 Vite 开发代理转发到后端，开发环境不需要在每个请求里写完整后端地址。

### 1. 替代方案

- 前端直接请求 `http://localhost:8080`：简单，但要处理 CORS 和环境地址切换。
- 后端开放任意来源 CORS：开发方便，但生产不安全。
- Nginx 统一反向代理：生产更合适，但本地开发配置成本更高。

### 2. 代价

- Vite Proxy 只解决开发环境，生产部署仍需要 Nginx 或后端网关。
- 代理配置错误时，页面看起来正常但 API 全部 404/502。

### 3. 失败场景

- 后端没启动：请求连接失败。
- Vite proxy target 写错：请求 502。
- 生产环境仍使用开发代理假设：部署后接口地址错误。

### 4. 当场改动

如果要部署生产，我会在 Nginx 中将 `/api` 代理到后端，并把前端 API 保持为相对路径。验证浏览器 Network、Nginx 日志和后端访问日志三处路径一致。

### 记忆方法

```text
开发：Vite Proxy
生产：Nginx/Gateway
前端：只写 /api
```

## 10. `ddl-auto: update` 有什么问题？

### 30 秒回答

当前项目学习阶段使用 `ddl-auto: update`，方便实体变化后自动补表和字段。它适合本地快速迭代，但不适合生产，因为 Hibernate 自动推断迁移不可审计、不可稳定回滚。后续应引入 Flyway，用版本化 SQL 管理 schema，并让 Hibernate 使用 `validate`。

### 1. 替代方案

- `create`：简单但会清空重建，风险很高。
- `validate` + Flyway：迁移可审计、可回滚，是生产方向。
- 手工 SQL：灵活但容易漏记录、漏环境。

### 2. 代价

- 当前 `update` 牺牲了迁移可审计性。
- 不同开发者环境可能产生不同 schema。
- 表结构变更和历史数据兼容没有显式脚本。

### 3. 失败场景

- 字段重命名被当成新增字段，旧数据没有自动迁移。
- 生产启动时自动改表，造成锁或数据风险。
- 多环境 schema 不一致。

### 4. 当场改动

我会先把当前数据库结构导出为 `V1__init_schema.sql`，新增字段用 `V2__...sql`，然后把 `ddl-auto` 改成 `validate`。验证全新数据库启动、已有数据库升级和回滚演练。

