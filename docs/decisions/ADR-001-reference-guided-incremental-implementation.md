# ADR-001: 采用参考项目驱动的渐进式实现路线

## Status

Accepted

## Date

2026-05-16

## Context

`interview-assistant` 是用户边学习边开发的智能面试助手项目，参考完整开源项目 `D:\work\work_space\Project\interview-guide`。参考项目已经具备完整平台能力，包括：

- 简历上传、解析、AI 分析、PDF 导出。
- 文字模拟面试、Skill 出题、AI 评估、历史详情、报告导出。
- Redis 缓存、限流和 Redis Stream 异步任务。
- 知识库、pgvector、RAG 问答和 SSE 流式响应。
- 面试日程、语音面试、前端页面和 Docker 部署。

当前项目已经完成后端 MVP 的主要链路：简历处理和文字面试流程。文字面试模块已经完成历史列表、历史详情、删除会话、独立答案表和报告聚合，并接入同步 AI 出题、AI 单题答案评估和规则兜底。项目仍未完成 Redis 异步任务、知识库、前端、PDF 导出和语音面试。

如果直接复制参考项目，会导致学习断层和大量不理解的复杂度。如果完全脱离参考项目，又容易在架构、接口和业务语义上走偏。

## Decision

采用“参考项目驱动 + 当前项目渐进式实现”的路线：

1. `interview-guide` 作为架构、业务语义和工程规范的首要参考。
2. `interview-assistant` 不机械复制参考项目，而是按当前学习阶段实现等价能力。
3. 每个新功能先对比参考项目做法，再决定当前阶段实现完整版本还是简化版本。
4. 每个阶段都要形成可运行、可验证的小闭环。
5. 当前继续使用 Maven 和 `com.interview` 包名，不迁移到参考项目的 Gradle 和 `interview.guide` 包名。
6. 当前 `questionsJson` 只作为题目快照保留，用户答案和评估结果已经拆到独立答案表。
7. AI 能力先采用同步调用 + 规则兜底，稳定后再演进为 Skill 驱动和异步任务。
8. Redis、RAG、前端、语音面试按依赖顺序逐步引入。

## Alternatives Considered

### 方案 A：直接复制 `interview-guide`

**Pros:**

- 功能完成速度最快。
- 代码结构和参考项目完全一致。

**Cons:**

- 用户学习收益低，容易只会运行不会解释。
- 大量依赖一次性引入，排错困难。
- 当前 Maven 项目结构和包名会被打乱。
- 不利于理解从 MVP 到完整项目的演进过程。

**Rejected:** 不符合“边学习边开发”的项目目标。

### 方案 B：完全独立设计，不参考 `interview-guide`

**Pros:**

- 自由度高。
- 可以完全按当前偏好设计。

**Cons:**

- 容易偏离原项目的业务语义和真实工程经验。
- 需要重复踩参考项目已经解决的问题。
- 最终很难靠齐完整平台能力。

**Rejected:** 本项目明确以 `interview-guide` 为参考实现。

### 方案 C：参考项目驱动的渐进式实现

**Pros:**

- 既保留学习过程，又能向成熟架构靠齐。
- 每个阶段都有可验证成果。
- 允许当前阶段简化，同时保留后续演进路径。
- 风险较低，适合长期迭代。

**Cons:**

- 完成完整项目的周期更长。
- 需要持续维护文档和计划。
- 某些同步方案后续需要重构，例如 AI 出题和 AI 评估从同步调用演进为 Skill/Redis Stream 编排。

**Accepted:** 最符合本项目目标。

## Consequences

- 文档中必须同时说明“当前阶段方案”和“后续参考项目方案”。
- 每次开发新功能前，应先查看 `interview-guide` 对应模块。
- 允许短期保留过渡设计，但必须知道何时替换。
- 项目完成顺序遵循依赖关系，而不是按兴趣跳跃开发。
- 后续所有大功能应在 `docs/implementation-plan.md` 中拆成可验收任务。

## Follow-up

- 按 `docs/implementation-plan.md` 继续推进，每次只做可验证的小闭环。
- 当前优先手工验证 AI 出题、答案提交、评估入库和报告展示完整链路。
- 链路稳定后补强核心 Service 测试。
- 再将同步 AI 出题演进为 Skill 驱动出题。
- AI 能力稳定后，再引入 Redis Stream 异步任务。
