# 接口限流实战：注解 + AOP + Redis 滑动窗口

本文记录 `interview-assistant` 接口限流的落地过程，包含取舍、代码结构、验证证据和踩坑记录。分两期完成：

| 期次 | 对应任务 | 实现 | 状态 |
| --- | --- | --- | --- |
| 第一期 | 任务 17 | Java 两步操作（`INCR` + `EXPIRE`），固定窗口 | 已被替代 |
| 第二期 | 任务 17.2 | Lua 脚本原子执行，滑动窗口 | 当前实现 |

保留第一期内容是为了记录“为什么要换”，直接看结论的读者可以跳到第四节。

## 一、为什么需要限流

项目里成本最高的接口有三个：创建面试（调 LLM 出题）、上传简历（调 LLM 分析）、单题评估（调 LLM 打分）。每次调用都要花 1~3 秒和真金白银，一个人连点十几次就能把额度和线程池同时打满。

限流的目的是**在超载时优雅地拒绝一部分请求**，而不是让整体崩掉。

## 二、三层结构

```text
@RateLimit(count = 3, interval = 1, timeUnit = TimeUnit.MINUTES)   ← 注解：声明规则
            ↓
RateLimitAspect（@Around）                                          ← 切面：拼 key、调用限流、放行或拦截
            ↓
RateLimitService.tryAcquire(key, limit, window)                     ← 执行 Lua 脚本
            ↓
Redis（ratelimit:类名.方法名:维度:标识，类型为 zset）
```

切点表达式用 `@annotation(rateLimit)` 直接绑定注解实例，省掉反射查注解；被拦下的请求抛 `RateLimitExceededException`，由 `GlobalExceptionHandler` 统一转成 `code=8001`。

## 三、四个关键决策

| 决策 | 选择 | 原因 |
| --- | --- | --- |
| 是否引入 AOP 依赖 | **不引** | Spring Boot 4 已停止发布 `spring-boot-starter-aop`（最新 4.0.0-M2）；`spring-boot-starter-data-jpa` → `spring-boot-data-jpa` → `spring-aspects` 已带入 `aspectjweaver`，AOP 自动配置仍在核心模块 |
| key 用什么构成 | **方法身份 + 维度 + 客户端标识** | 绝不能用 `count` 这种配置值：两个接口限额相同时 key 会撞车，改配置还会让计数“重置”送免费额度 |
| IPv6 的冒号怎么处理 | **取到 IP 后 `replace(':', '_')`** | key 用 `:` 分层，IPv6 自带 8 个冒号会破坏分段，使前缀扫描失效 |
| 检查与扣减怎么保证原子 | **放进同一个 Lua 脚本** | Java 里“先判断再写入”两步之间有空隙，高并发下会多放行；Redis 执行脚本期间不处理其他命令 |

key 的最终形态：

```text
ratelimit:InterviewController.createInterview:ip:0_0_0_0_0_0_0_1
└─前缀───┘ └──────方法身份──────────────┘ └维度┘ └──客户端──┘
```

三层隔离全部体现在 key 里：换接口、换维度、换客户端，都不会互相干扰。

## 四、从固定窗口到滑动窗口

### 4.1 第一期：固定窗口的两个问题

```java
RAtomicLong counter = redissonClient.getAtomicLong(key);
long current = counter.incrementAndGet();
if (current == 1) {
    counter.expire(window);
}
return current <= limit;
```

第一个问题：**`INCR` 与 `EXPIRE` 是两条独立命令**，中间可以插进其他请求。如果进程恰好在两句之间挂掉，key 就没有过期时间，计数会永远累积。

这引出 `current == 1` 这个写法：只在第一次请求时设过期。不能每个请求都设，因为 `expire` 会把倒计时重新拨回起点——用户只要持续访问，窗口就永远不结束，计数只增不减，等于永久封禁。这个陷阱很隐蔽，只有“后续请求不重置 TTL”这条断言能抓到它。

第二个问题：**固定窗口按整段时间切分，边界处额度翻倍**。

```text
12:00 这一分钟：额度 10 次
12:01 这一分钟：额度 10 次

12:00:59 用满 10 次
12:01:00 窗口重置，再用满 10 次
→ 实际 2 秒内放进了 20 个请求，是期望上限的 2 倍
```

限流的目的是保护下游，而下游最怕的正是这种瞬时峰值。

### 4.2 第二期：滑动窗口

滑动窗口不看整段时间，而是**每次请求都回头看最近 N 秒**：

```text
判断依据：过去 60 秒内已经有几次请求？
```

没有“整个窗口集体清零”的动作，所以不存在边界翻倍。

实现方式叫**滑动窗口日志**：把每次成功请求的时间戳记进一个有序集合，每次请求先按时间戳剪掉滑出窗口的记录，再数数。

### 4.3 Lua 脚本实现

`server/src/main/resources/scripts/rate_limit.lua`：

```lua
local key = KEYS[1]
local nowMs = tonumber(ARGV[1])
local windowMs = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local requestId = ARGV[4]

-- 1. 清掉窗口外的历史记录
redis.call("ZREMRANGEBYSCORE", key, 0, nowMs - windowMs)

-- 2. 数一下窗口内还剩几次
local used = redis.call("ZCARD", key)

-- 3. 超限直接返回，不写入
if used >= limit then
    return 0
end

-- 4. 记下这次请求，并把整个集合的过期时间设为窗口长度
redis.call("ZADD", key, nowMs, requestId)
redis.call("PEXPIRE", key, windowMs)

return 1
```

四条命令各自的职责：

| 命令 | 作用 |
| --- | --- |
| `ZREMRANGEBYSCORE key 0 now-window` | 删掉分数早于剪枝线的成员，这就是“滑动” |
| `ZCARD key` | 数出窗口内已用次数 |
| `ZADD key now requestId` | 记录本次请求，分数用毫秒时间戳 |
| `PEXPIRE key windowMs` | 兜底防止 key 永久驻留（窗口结束由剪枝负责，TTL 只防内存泄漏） |

三个容易踩的细节：

- ZSet 成员不能重复，所以用 UUID 当成员。同一毫秒的两次请求如果用固定字符串，会互相覆盖，只算一次。
- `ARGV` 拿到的是字符串，必须 `tonumber`，否则算术运算报 `attempt to perform arithmetic on a nil value`。
- 剪枝线用闭区间 `[0, now-window]`，边界上会多删一毫秒，实际影响可以忽略。

### 4.4 Java 侧调用

```java
RScript rScript = redissonClient.getScript(StringCodec.INSTANCE);
Object result = rScript.eval(
        RScript.Mode.READ_WRITE,      // 脚本会写数据
        LUA_SCRIPT,                   // 直接传内容，Redisson 管理 SHA 缓存与 NOSCRIPT 回退
        RScript.ReturnType.LONG,      // Lua 的 return 1 映射为 Long
        List.of(key),                 // KEYS
        String.valueOf(System.currentTimeMillis()),
        String.valueOf(windowMs),
        String.valueOf(limit),
        UUID.randomUUID().toString());
```

要点：

- 脚本内容在 `static` 块里用 `ClassPathResource` 读一次，放进 `static final String`。读取失败抛 `IllegalStateException`，让应用启动即失败，限流不允许静默失效。
- `RScript.ReturnType` 在 Redisson 4.0 里改过名：3.x 的 `INTEGER` 变成 `LONG`。抄示例代码时以本地 jar 为准。
- 参数顺序必须和脚本里的 `KEYS` / `ARGV` 严格对应。错位不会报错，只会行为诡异。
- 返回的 `Long` 与 `1L` 比较时用 `Long.valueOf(1L).equals(result)`，不要用 `==` 比对象。

## 五、验证证据

| 证据 | 内容 |
| --- | --- |
| 单元测试 | `RateLimitServiceTest` 4 个用例全绿：限额内放行、超额拒绝、窗口到期重置、被拒请求不写入记录 |
| 接口验证 | 1 分钟内第 4 次创建面试返回 `code=8001`，日志 `触发限流: key=..., limit=3, windowMs=60000` |
| 数据结构 | `TYPE` 返回 `zset`；`ZCARD` 等于成功次数而非总请求数；`ZRANGE ... WITHSCORES` 能看到时间戳 |
| key 隔离 | 创建面试与简历上传各有一条 key，后者额度不受前者消耗 |
| 异常链路 | 无需新增代码，`GlobalExceptionHandler` 对 `BusinessException` 的统一处理直接覆盖 |

手动验证脚本本身（不经过 Java）：

```powershell
docker cp server\src\main\resources\scripts\rate_limit.lua redis:/tmp/rate_limit.lua
docker exec redis redis-cli --eval /tmp/rate_limit.lua test:lua ',' 1000000 60000 2 req1
docker exec redis redis-cli --eval /tmp/rate_limit.lua test:lua ',' 1000100 60000 2 req2
docker exec redis redis-cli --eval /tmp/rate_limit.lua test:lua ',' 1000200 60000 2 req3
docker exec redis redis-cli --eval /tmp/rate_limit.lua test:lua ',' 1070000 60000 2 req4
docker exec redis redis-cli DEL test:lua
```

预期 `1 / 1 / 0 / 1`：前两次放行，第三次被拒，第四次因为时间跨过窗口、旧记录被剪掉而重新放行。

PowerShell 里那个逗号必须加引号写 `','`。裸逗号会被 PowerShell 当作数组运算符吞掉，导致所有参数被当成 KEYS、ARGV 为空，脚本报 `nil value`。

## 六、换算法之后测试怎么改

第一期有个用例断言“后续请求不重置 TTL”。换成滑动窗口后它变红了：

```text
Expecting actual: 9997L
to be less than:   9995L
```

原因是脚本每次成功请求都执行 `PEXPIRE`，TTL 被刷新回满值。这不是功能坏了，而是**测试绑定了实现细节**。

| 窗口类型 | 防“计数永生”的手段 | TTL 是否该重置 |
| --- | --- | --- |
| 固定窗口 | 只能靠第一个请求设过期 | 不能重置 |
| 滑动窗口 | 每次请求清理过期记录，窗口结束由剪枝决定 | 可以重置，TTL 只防内存泄漏 |

所以处理方式是**替换断言，而不是改数字让它变绿**。新用例验证的是一条任何算法都必须满足的契约：

```java
assertThat(rateLimitService.tryAcquire(key, limit, window)).isTrue();
assertThat(rateLimitService.tryAcquire(key, limit, window)).isTrue();
assertThat(rateLimitService.tryAcquire(key, limit, window)).isFalse();
assertThat(rateLimitService.tryAcquire(key, limit, window)).isFalse();
assertThat(redissonClient.getScoredSortedSet(key, StringCodec.INSTANCE).size()).isEqualTo(limit);
```

“被拒绝的请求不占用额度”在固定窗口、滑动窗口、令牌桶里都成立，将来再换算法也不用改这个测试。

读这个集合必须传 `StringCodec.INSTANCE`，和写入时的 codec 保持一致。用默认 Kryo codec 会给 key 名字加编码头，读到的其实是另一个 key。

## 七、已知局限

| 局限 | 后果 | 后续方向 |
| --- | --- | --- |
| IP 可伪造 | 直接信任 `X-Forwarded-For` 可被绕过 | 约定可信代理层数，或把限流放到网关层 |
| `USER` 维度退化为全局限流 | 无登录体系，统一归入 `anonymous` | 引入用户体系后改为从登录信息取 |
| 一个方法只能配一条规则 | 无法同时限制“每分钟 3 次”和“每天 100 次” | 参考项目用 `@Repeatable` + 一次脚本调用处理多条规则 |
| 超限直接抛异常 | 无法降级到兜底实现 | 参考项目支持 `fallback` 指定降级方法 |
| 固定窗口语义的残留说明 | 早期文档和注释若仍写“固定窗口”，会误导后来者 | 修改实现时同步更新注释 |

## 八、与参考项目的差距

参考项目 `interview-guide`（master 提交 `ebe2697a`，2026-10-09）的限流实现：

| 能力 | 参考项目 | 当前项目 |
| --- | --- | --- |
| 存储结构 | `key:value` 存可用令牌数 + `key:permits` 用 ZSet 记录每次申请 | 单个 ZSet 记录请求时间戳 |
| 算法 | 令牌桶式：窗口内过期记录把令牌还回去，允许攒额度 | 滑动窗口日志：严格“最近 N 秒不超过 N 次” |
| 多规则 | `@Repeatable`，一次脚本调用原子检查多条规则，任一不过则全部回滚 | 单条规则 |
| 超限处理 | 支持 `fallback` 降级方法 | 抛业务异常 |
| 脚本调用 | `scriptLoad` 缓存 SHA + `evalSha`，捕获 `NOSCRIPT` 手动重载 | 传脚本内容，Redisson 内部管理 SHA 与回退 |
| key 设计 | 用 `{类名:方法名}` 作 hash tag，保证同方法多维度规则落在同一节点 | 无 hash tag（单机阶段够用） |

两个实现的共同点是“检查 + 扣减必须在一次脚本调用里完成”，差别在于**是否允许突发**。令牌桶允许把窗口内没用掉的额度攒起来一次性用掉，滑动窗口不允许——选哪个取决于业务：LLM 接口更适合滑动窗口（下游扛不住突发），对外开放 API 更适合令牌桶（对调用方更友好）。

## 九、命令速查

```powershell
# 查看所有限流 key
docker exec redis redis-cli KEYS 'ratelimit:*'

# 查看数据结构（应为 zset）
docker exec redis redis-cli TYPE 'ratelimit:InterviewController.createInterview:ip:0_0_0_0_0_0_0_1'

# 查看窗口内已记录的请求数
docker exec redis redis-cli ZCARD 'ratelimit:InterviewController.createInterview:ip:0_0_0_0_0_0_0_1'

# 查看每条记录的时间戳
docker exec redis redis-cli ZRANGE 'ratelimit:InterviewController.createInterview:ip:0_0_0_0_0_0_0_1' 0 -1 WITHSCORES

# 查看剩余毫秒数
docker exec redis redis-cli PTTL 'ratelimit:InterviewController.createInterview:ip:0_0_0_0_0_0_0_1'

# 手动清空以便重新验证
docker exec redis redis-cli DEL 'ratelimit:InterviewController.createInterview:ip:0_0_0_0_0_0_0_1'
```

两个判断要点：

- `ZCARD` 应当等于**成功次数**。如果它随着被拒请求一起增长，说明脚本里的“先判断再写入”被改坏了。
- `ZRANGE` 里的时间戳应当随着窗口滑动逐步消失。如果集合只增不减，说明 `ZREMRANGEBYSCORE` 的剪枝线算错了。
