# 接口限流实战：注解 + AOP + Redis 固定窗口

本文记录 `interview-assistant` 第一期接口限流的落地过程，包含取舍、代码结构和验证证据。对应实施计划任务 17，完成日期 2026-11-03。

## 一、为什么需要限流

项目里成本最高的接口有三个：创建面试（调 LLM 出题）、上传简历（调 LLM 分析）、单题评估（调 LLM 打分）。每一次调用都要花 1~3 秒和真金白银。如果不加约束，一个人连点十几次就能把额度和线程池同时打满。

限流的目的是**在超载时优雅地拒绝一部分请求**，而不是让整体崩掉。

## 二、三层结构

```text
@RateLimit(count = 3, interval = 1, timeUnit = TimeUnit.MINUTES)   ← 注解：声明规则
            ↓
RateLimitAspect（@Around）                                          ← 切面：拼 key、判断、放行或拦截
            ↓
RateLimitService.tryAcquire(key, limit, window)                     ← 计数：INCR + EXPIRE
            ↓
Redis（ratelimit:类名.方法名:维度:标识）
```

切点表达式用 `@annotation(rateLimit)` 直接绑定注解实例，省掉反射查注解；被拦下的请求抛 `RateLimitExceededException`，由 `GlobalExceptionHandler` 统一转成 `code=8001`。

## 三、三个关键决策

| 决策 | 选择 | 原因 |
| --- | --- | --- |
| 是否引入 AOP 依赖 | **不引** | Spring Boot 4 已停止发布 `spring-boot-starter-aop`（最新 4.0.0-M2）；`spring-boot-starter-data-jpa` → `spring-boot-data-jpa` → `spring-aspects` 已带入 `aspectjweaver`，AOP 自动配置仍在核心模块 |
| key 用什么构成 | **方法身份 + 维度 + 客户端标识** | 绝不能用 `count` 这种配置值：两个接口限额相同时 key 会撞车，改配置还会让计数“重置”送免费额度 |
| IPv6 的冒号怎么处理 | **取到 IP 后 `replace(':', '_')`** | key 用 `:` 分层，IPv6 自带 8 个冒号会破坏分段，使前缀扫描失效 |

key 的最终形态：

```text
ratelimit:InterviewController.createInterview:ip:0_0_0_0_0_0_0_1
└─前缀───┘ └──────方法身份──────────────┘ └维度┘ └──客户端──┘
```

三层隔离全部体现在 key 里：换接口、换维度、换客户端，都不会互相干扰。

## 四、`current == 1` 才设过期

`RateLimitService.tryAcquire` 的核心四行：

```java
RAtomicLong counter = redissonClient.getAtomicLong(key);
long current = counter.incrementAndGet();
if (current == 1) {
    counter.expire(window);
}
return current <= limit;
```

必须用 `getAtomicLong` 而不是 `getBucket`，只有前者提供原子自增。

只在 `current == 1` 时设过期，是因为 `expire` 每调用一次都会把倒计时**重新拨回起点**。如果每个请求都设，只要用户持续访问窗口就永远不结束，计数只增不减，等于**永久封禁**。这是限流实现里最常见的 bug。

## 五、验证证据

| 证据 | 内容 |
| --- | --- |
| 单元测试 | `RateLimitServiceTest` 4 个用例全绿：限额内放行、超额拒绝、窗口到期重置、后续请求不重置 TTL |
| 接口验证 | 1 分钟内第 4 次创建面试返回 `code=8001`，日志 `触发限流: key=..., current=4, limit=3` |
| key 隔离 | `KEYS 'ratelimit:*'` 同时存在创建面试和简历上传两条 key，后者的额度不受前者消耗影响 |
| 异常链路 | 无需新增代码，`GlobalExceptionHandler` 对 `BusinessException` 的统一处理直接覆盖 |

其中第 4 个测试用例最关键：前三个用例在删掉 `if (current == 1)` 后仍然全绿，只有“后续请求不重置 TTL”会失败。**测试的价值不是证明功能可用，而是证明错误实现会失败。**

## 六、已知局限

| 局限 | 后果 | 解决方向 |
| --- | --- | --- |
| `INCR` 与 `EXPIRE` 非原子 | `expire` 失败时 key 无过期时间，计数一直累积 | 任务 17.2：Lua 脚本 |
| 固定窗口边界翻倍 | 窗口交界处最坏放行 2 倍流量 | 任务 17.2：滑动窗口 |
| 超限请求仍然 `INCR` | 被刷时每次请求都写一次 Redis | 任务 17.2：脚本内先判断再扣减 |
| IP 可伪造 | 直接信任 `X-Forwarded-For` 可被绕过 | 上线前约定可信代理层数或改在网关层限流 |
| `USER` 维度退化为全局限流 | 无登录体系，统一归入 `anonymous` | 引入用户体系后改为从登录信息取 |

## 七、与参考项目的差距

参考项目 `interview-guide` 的限流能力更完整：

| 能力 | 参考项目 | 当前项目 |
| --- | --- | --- |
| 实现方式 | Lua 脚本，滑动窗口（`ZSET` 存时间戳） | Java 两步操作，固定窗口 |
| 注解 | 支持 `@Repeatable`，一个方法多条规则叠加 | 单条规则 |
| 超限处理 | 支持 `fallback` 指定降级方法 | 统一抛业务异常 |
| 脚本管理 | 缓存 SHA，处理 `NOSCRIPT` 重载 | 无脚本 |
| 限流维度 | GLOBAL / IP / USER | GLOBAL / IP / USER（USER 退化） |

差异的核心是“原子性”和“窗口精度”，这两点集中在任务 17.2 解决。

## 八、命令速查

```powershell
# 查看所有限流 key
docker exec redis redis-cli KEYS 'ratelimit:*'

# 查看某个接口的当前计数
docker exec redis redis-cli GET 'ratelimit:InterviewController.createInterview:ip:0_0_0_0_0_0_0_1'

# 查看剩余窗口时间（秒）
docker exec redis redis-cli TTL 'ratelimit:InterviewController.createInterview:ip:0_0_0_0_0_0_0_1'

# 手动清空以便重新验证
docker exec redis redis-cli DEL 'ratelimit:InterviewController.createInterview:ip:0_0_0_0_0_0_0_1'
```

`TTL` 应当随着请求到来持续递减，**不会因为新请求跳回上限**。如果发现它每次都被重置，说明 `if (current == 1)` 判断写错了。
